# AI 협업 방식과 나의 역할

## 역할 분담

| 영역 | 내가 담당한 판단 | AI를 활용한 작업 |
|---|---|---|
| 목적 설정 | 어떤 제작 자유도를 제공할지, 기존 생성기에서 무엇을 유지할지 결정 | 요구사항 질문, 모호한 조건과 예외 정리 |
| 설계 | 공간·아트·포털 책임, 데이터 단위, 입력과 확정 정책 결정 | 대안 비교, 명세와 수용 기준 초안 작성 |
| 구현 | 범위 설정, 제안 수정과 우선순위 결정 | C#·UXML·USS 코드 작성 및 수정 |
| 검증 | 검증 범위 선택, 실제 사용 피드백, 보류 항목 결정 | 코드 검토, Unity 내부 이벤트·런타임 검사, 화면 조작 및 증거 기록 |
| 문서화 | 발표 목적과 강조할 내용 지정 | 핸드오프, 매뉴얼, 화면 자료 정리 |

실제 대화에서는 AI의 제안을 그대로 채택하기보다, 수치 입력 대신 기즈모 사용, 이동 확인창과 즉시 회전의 차이, 포털 폭·높이 고정과 깊이 편집, 셀 자동 추정 제외 등을 반복적으로 정정했습니다.

## 반복한 개발 흐름

```text
사용 목적 설명
→ AI 질문으로 빠진 결정 확인
→ 내가 범위와 정책 결정
→ 명세·수용 기준·핸드오프 작성
→ AI 구현
→ 코드 검토 / Unity 실행 / 화면 확인
→ 실패 근거와 사용 피드백
→ 수정 및 재검증
```

Codex 기반 코드·도구 작업과 질문형 스킬(grill 계열)을 활용했습니다. Unity 내부 검사와 Computer Use 화면 조작을 함께 사용했으며, 화면 조작 권한 문제로 실행하지 못한 검사는 통과로 기록하지 않았습니다. 필요한 대화상자는 직접 처리하며 검증을 이어갔습니다.

## 이 과정에서 배운 점

- 구현 요청 전에 입력 상태, 취소 시점, 저장 단위와 기존 시스템의 불변 조건을 정해야 합니다.
- 컴파일 성공, 코드상 정상, 내부 이벤트 검사, 실제 OS 입력 검사는 서로 다른 근거입니다.
- AI가 구현한 기능도 기존 편집 상태와 결합하면 문제가 발생할 수 있습니다. 자동 편입과 Play의 충돌이 그 사례였습니다.
- 명세와 기록이 쌓이면 이전 설명이 현재 코드와 어긋납니다. 최신 코드와 검증 기록을 우선해 문서를 갱신했습니다.

코드 라인별 수작업·AI 비율이나 생산성 향상률은 측정하지 않았습니다. 이 저장소는 AI 도움을 숨기지 않고, 요구사항·설계 판단·검증 과정과 함께 결과물을 공개합니다.
